# Kubernetes (k8s) Notes

## Overview

- Platform used to orchestrate deployment, scaling, and management of container-based applications.

Common tasks:

- Balancing load between nodes
- Managing updates
- Mounting storage systems
- Accessing app logs
- Distributing secrets
- Debugging applications
- Monitoring resources

---

## How a Container Runs in a Cluster

### Control Plane

- Responsible for managing the state of the cluster
- Runs on multiple nodes/zones

#### API Server

- Primary interface between the control plane and the rest of the cluster
- Exposes a REST API that allows clients to interact with the control plane and submit requests to manage the cluster

#### etcd

- Distributed key-value store
- Stores the cluster's persistent state
- Used by other components to store and retrieve info on the cluster

#### Scheduler

- Responsible for scheduling pods onto the worker nodes
- Uses info about the resources required by the pods and the available resources on the worker nodes to make placement decisions

#### Controller Manager

- Responsible for running controllers that manage the state of the cluster
- e.g. replication, deployment

---

### Worker Nodes

#### Kubelet

- Node agent that runs on each worker node
- Responsible for communicating with the control plane
- Receives instructions and ensures the desired state is maintained

#### Container Runtime

- Runs the containers
- Responsible for pulling container images from a registry, starting and stopping a container, and managing container resources

#### Kube-Proxy

- Routes traffic to the correct pods
- Also does load balancing
### Pods: 
- the smallest deployable unit



## Namespaces

A way to split a cluster into virtual partitions. Within the same cluster you can have multiple namespaces, each with its own apps, completely separate from the others.

- Isolation of resources from other namespaces
- Resource allocation
- RBAC (role-based access control)

## Pod States

| State | Meaning |
| --- | --- |
| **Pending** | Accepted by the API server but not running yet. Could mean the scheduler is still deciding which node to run the pod on. |
| **Running** | At least one container is up. This only means the container is running; it could still be throwing errors. |
| **Succeeded** | All containers have exited with code 0. |
| **Failed** | All containers have terminated, and at least one exited with a non-zero code. |
| **Unknown** | The cluster can't determine the state (kubelet not responding, networking issue, etc.). |

## Deployments

- A controller that helps you manage an application across multiple instances
- Helps you create and update pods, and ensures the correct number are running
- Makes it easy to manage at large scale
- Allows you to scale automatically when needed
- Easy to roll back

## ReplicaSets

- Ensure a specified number of pods are running at any given time
- Automatically replace pods that die
- Do not have the rolling update and rollback abilities that Deployments have
- During a rollout, a Deployment creates two different ReplicaSets, which are responsible for how many pods of each version are running

## Container Types

### Init Containers

- Run before the actual containers start, before the real workload
- Run in the order they are listed in the YAML
- Must exit successfully (exit 0)
- If one init container fails, the pod doesn't start (used for things that are critical for startup)

### Sidecar Pattern

A container that runs alongside the main app and extends it.

- Shares the same networking and volumes as the main container
- Can talk over localhost
- Examples:
  - **Log shipping:** the app writes logs to a file and the sidecar watches the file and ships the logs
  - **Service mesh:** a proxy sidecar is injected into every pod so all traffic flows through that proxy
  - **Auth agent:** the sidecar updates secrets from a vault when they are rotated

### Adapter Containers

Used when the app outputs data in one format and you need it in another. The adapter does the conversion.

- **Metrics:** a legacy app exposes metrics in a proprietary format and the adapter converts it to Prometheus format
- **Logs:** a container outputs logs in a weird format and the adapter reformats them
- **APIs:** REST → gRPC
- Good when you can't change the app's code

### Ephemeral Containers

- Let you attach a debug container to a running pod without restarting it
- Inject a temporary container with the tools you need
- Ideal for debugging crashed or stuck containers
- Do not affect the pod lifecycle

## QoS (Quality of Service)

When a pod is squeezed for resources (memory, CPU), Kubernetes uses QoS classes to decide which pods get evicted.

| Class | Condition | Eviction order |
| --- | --- | --- |
| **Guaranteed** | Every container in the pod has requests equal to limits, no more, no less. | Evicted last |
| **Burstable** | At least one container has a request lower than its limit. | Evicted second |
| **BestEffort** | No requests or limits set. | Evicted first when pressure hits |

## Probes

Health checks run by Kubernetes to check and monitor container state.

- **Liveness:** checks if the container is still alive. If not, it is restarted.
- **Readiness:** checks if the container is ready to serve traffic. If not, the pod is removed from the Service endpoints.
- **Startup:** checks if the app has fully started. Useful for slow apps; disables the other probes until it succeeds.

## Rolling Updates

- Gradually replaces old pods with new ones with no downtime
- When you update the image of a container, Kubernetes starts replacing the old ReplicaSet with a new one
- You will have a mix of old and new pods; as new pods become ready, old ones are terminated
- **maxSurge:** how many extra pods can exist during the rollout
- **maxUnavailable:** the maximum number of pods that can be down at one point (ensures most of the capacity keeps serving traffic)

## Recreate Strategy

- All pods terminate, then new pods spin up
- Creates downtime
- Used for database migrations where there is a difference in schema
- Also used for storage conflicts: two pods can't access the same volume, so one has to die before the other can attach

## Rollbacks

- Kubernetes keeps a history of old deployments by keeping the old ReplicaSets around, scaled to 0
- A rollback scales up the old ReplicaSet and scales down the current one
- 10 revisions are kept by default (can be lowered to save resources)
- Revision history is stored in etcd

## Resource Requests and Limits

Every container tells Kubernetes what it needs and what it can take.

- **Requests:** the minimum guaranteed amount. The scheduler uses this to place pods. For example, if a container requests a certain amount of CPU, the scheduler finds a node that has it available.
- **Limits:** the maximum allowed. The container can use up to this amount and no more.
  - CPU: throttled when the limit is reached
  - Memory: the container is OOM killed when the limit is reached

**Units**

- CPU is measured in millicores: 1000m = one core
- Memory is measured in bytes (e.g. Mi, Gi)

**If not set**

- No request: the pod can land on an overloaded node
- No limit: the container could use whatever is available

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"
```

## Limit Ranges

- A policy object that enforces resource boundaries per container or per pod
- Used to define minimum and maximum CPU and memory
- Applies defaults if none are specified

## Resource Quotas

- Limit total consumption across an entire namespace
- If a new pod would push a namespace over its quota, it is rejected at the admission level
- Prevents one team's namespace from consuming the entire cluster's resources
- Can also limit other objects, such as PVCs, Secrets, and ConfigMaps
